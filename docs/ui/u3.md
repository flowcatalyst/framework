# The orders application: U3 results (2026-10-15)

Milestone U3 of [`../go/ui.md`](../go/ui.md) section 17: an example single-page application on the
shared UI package, on a **real backend**: the Java `examples/orders-demo`, which serves it from its
jar with the strict CSP, signs users in with the framework's sessions (M4c) and answers the typed
orders API (MO). Exit: "list, drawer and add-line form against the real server, validation errors on
fields, E2E green". Components and partials are in [`u1.md`](u1.md) and [`u2.md`](u2.md); this page is
what building a real application on them found.

## What was built

| Part | Where |
|---|---|
| The application | `ui/apps/orders` (`@flowcatalyst/orders-web`), in the UI workspace. Depends on `@flowcatalyst/ui` and `@flowcatalyst/api-runtime` by path (`link:../../packages/...`, the way an application in another repository does it: one Vue in the bundle, checked) |
| Pages | Orders (list with URL-backed status filter, search of the loaded page, cursor paging, `New order` form dialog), the order drawer as a child route (`/orders/:id`: details, lines, `Add line` form dialog, cancel with a reason and a confirm dialog), Signed out, Sign-in failed, Not permitted, Unavailable, Not found |
| Client | `src/api/orders`, generated by `fwOpenApiConfig` from `examples/orders-demo/web/openapi.json` (`pnpm --filter @flowcatalyst/orders-web generate`; `drift` is part of `pnpm api:drift`) |
| Build output | `vite build` writes `examples/orders-demo/web/dist` (git-ignored); the demo's pom copies it under `fw-spa` (Maven never runs Node) |
| Serving | `OrdersSpaModule` mounts `Spa.classpath("fw-spa")` with `Csp.strict(<colour-mode snippet hash>)`; `OrdersSpaTest` runs `SpaTesting.assertServesBuild` and proves the policy's one hash is the hash of the one inline script in the built `index.html` (skipped, loudly, when `web/dist` is not built) |
| Sign-in | `OrdersWeb`: `postLogoutRedirect("/signed-out")`, `loginFailure(LoginFailureHandler.redirectTo("/sign-in-failed"))` |
| End-to-end | `ui/apps/orders/e2e` (Playwright, Chromium) against the real demo: `scripts/start-backend.ts` builds the demo with Maven and starts `OrdersE2e` (test class): the real `OrdersWeb`, Testcontainers PostgreSQL on a random port, and `TestOidcProvider` standing in for the platform (it signs in at once, with the roles the suite asks for through a control server). Ports 4392 (application) and 4393 (control); never 8080 or 15432, no developer database |
| Run it | `pnpm orders:e2e` (also the last step of `pnpm check`); `pnpm --filter @flowcatalyst/orders-web screenshots` (every state, light and dark, desktop and phone, into `screenshots/`); Maven offline with `MAVEN_ARGS=-o` |
| Development | `pnpm orders:dev`: Vite on 5175 proxies `/api` and `/auth` to the backend (`ORDERS_BACKEND`, default `http://127.0.0.1:18080`); the backend's `auth.public-base-url` is the Vite origin (contract section 9). `start-backend.ts --public http://127.0.0.1:5175` starts the test backend that way |

## Results

- `tests/e2e`: **28 passed** (auth 9, orders 11, axe 5, SPA serving 3), 4 screenshot cases skipped
  without `SCREENSHOTS=1`. `pnpm check` is green (gallery e2e 90 passed, api-runtime 37, ui 49).
  Java: `OrdersApiTest`, `OrdersConformanceTest`, `OrdersOpenApiTest`, `OrdersDemoTest` (17) and the
  new `OrdersSpaTest` (3).
- **Every test runs a CSP monitor** (`e2e/fixtures.ts`): no `securitypolicyviolation`, no console
  message about the policy, no request to another origin, no uncaught page error. The demo's strict
  policy is the one `@flowcatalyst/ui/csp` builds (asserted equal in `spa.spec.ts`).
- **Axe at WCAG 2.2 AA, strict, zero violations**: the list (empty and filled), not found, signed out,
  sign-in failed, not permitted, the drawer, the new-order and add-line dialogs with errors, the
  discard and the confirm dialogs, a toast over the drawer, the filters popover; light and dark;
  desktop and 390 px. G2 (since fixed) was the one exception.
- Real-browser findings the in-page gallery could not give: the whole sign-in round trip (anonymous
  visit, `/auth/login?returnTo=`, provider, callback, cookie, back to the deep link), an ended session
  noticed by the next call and by window focus, sign-out and the platform's post-logout redirect, a
  viewer's read-only UI and the server's `403` for the same write, a user with no role, a refused
  sign-in, a `409` business rule shown in the dialog, a stale cancel, `503`, `403` and an offline fetch
  as toasts, hashed assets `immutable`, a stale chunk a `404` never the shell.
- hey-api's `int64` Zod setting from U2 held: `unitPriceCents` leaves the form as a JSON number
  (`{"sku":"PUNCH-CARDS","quantity":500,"unitPriceCents":3}`, asserted).

## Gaps found in the UI kit and the framework

Each row: what was missing or wrong, what was done. "Fixed" means a commit in this repository.

| # | Gap | What was done |
|---|---|---|
| G1 | The Java `Spa` default was the baseline CSP although the contract (section 7) says strict is the default; the hash is a string the application must copy from `@flowcatalyst/ui/csp` | **Fixed (default)**: `Spa` defaults to `Csp.strict()` (no hashes), the baseline is the opt-in; `SpaTest` and the regenerated `http/spa.json` pin the default, Go's vector test uses its default too; BREAKING entry in the handover. **Remaining**: the hash is still passed by the application (the demo does; `OrdersSpaTest` checks it against `index.html`); shipping it with the SPA (a `csp-hashes` file Vite writes) is not built |
| G2 | `FwAppShell`'s user menu was a modal dropdown: while open, Reka marked the sidebar and the page `aria-hidden` while focus could still reach them (axe `aria-hidden-focus`, strict) | **Fixed**: `:modal="false"` on the shell's `UDropdownMenu`, as `FwRowActions` does. Axe now runs on the open user menu in the orders e2e and in the gallery overlays test (light and dark); a gallery test covers Escape, outside click and focus return |
| G3 | Form errors showed Zod's developer text (`Invalid string: must match pattern /^(?:[A-Z0-9][A-Z0-9-]*)$/`, `Too small: expected string to have >=1 characters`) | **Fixed**: `@flowcatalyst/api-runtime` sets Zod's `customError` (`zod-config.ts`, `userMessage`): "This field is required.", "Enter at most 64 characters.", "Enter a value in the expected format.", "Must be at least 1.", ... Unit-tested; the gallery's assertion updated. A schema cannot say what a pattern means ("upper-case letters and digits"): the generated schemas carry no `description`, so a field's `help` text says it (the form shows both) |
| G4 | `FwListPage` has no phone strategy: a table with five columns is clipped at 390 px (Status cut off, no hint it scrolls) | Worked around in the application (`meta.class`: numeric columns `hidden sm:table-cell`, tighter cell padding, smaller id). | G5 | The non-modal drawer overlays the list: Filters, Refresh and the right-hand columns are unreachable while a record is open (Playwright: "subtree intercepts pointer events") | Not fixed (a design choice of the kit's drawer; the user closes it with Escape). The tests do the same. Worth a `push` layout on wide screens |
| G6 | The lint ignore of generated clients listed `apps/gallery/src/api/**` only: a second application's generated folder failed lint | **Fixed**: `apps/*/src/api/**` |
| G7 | `pnpm check` ran only the gallery's e2e | **Fixed**: `orders:e2e` is the last step; `orders:dev` added. Side effect: `pnpm build` (`-r`) now also writes `examples/orders-demo/web/dist`, outside `ui/` |
| G8 | `flowcatalystUi()`'s CSS lift ran in the dev server and failed on vaul-vue's pre-bundled shape ("a vite-plugin-css-injected-by-js block in an unknown shape"): **no application could run `vite` in development** (the gallery too; U0 to U2 only built) | **Fixed**: the lift runs for production builds only (`configResolved`); the dev server has no CSP. ## Design notes

- **Where the application lives.** The pom's resource (`web/dist` under `fw-spa`) and the committed
  `openapi.json` are in `examples/orders-demo/web/`; the application's source is in the UI workspace
  (`ui/apps/orders`) so that `pnpm check` lints, typechecks, drifts and tests it with the kit, and its
  Vite build and generator point at the demo's folder. An application in another repository has its
  own `web/` with the same `package.json` shape and `link:` dependencies (README).
- **`/orders` is a client route** and the server has none under that first segment (its API is
  `/api/orders`): contract section 5, checked by `OrdersSpaTest` and `spa.spec.ts`.
- **Permissions show and hide, the server decides.** The sidebar entry, `New order`, `Add line` and the
  cancel section follow `session.can(...)`; a viewer's write is refused by the server (`403`) in the
  same test. A user with no role goes to `Not permitted` (route `meta.permission`), not to a broken list.
- **No timers on the session.** The session is read once and again on window focus (a test dispatches
  the event after ending the session on the server); a `401` on any call starts sign-in.
- **The cancel flow** is: type a reason in the drawer (the API requires one), `Cancel order…` asks
  (`useConfirm`, `Keep order` is the focused answer), a `409` (changed meanwhile) is a toast and the
  drawer reloads the order. Typing a reason and leaving asks "Discard changes?" through `useDirtyForm`.
- **The test provider changes who signs in** (`/control/sign-in-as?roles=`), so one backend serves clerk,
  viewer and no-role users; `freshData()` truncates the orders before each test. One Playwright worker:
  the tests share one database.

## Not verified

- Only Chromium (as U0). Firefox and WebKit not run.
- A real platform: the sign-in is against `TestOidcProvider`, which is shaped like the platform
  (sessions contract section 9). The platform must have `{public-base-url}/auth/callback` and
  `{public-base-url}/signed-out` (post-logout redirect) registered for the login client; nothing here
  proves that.
- The Vite dev proxy is verified by hand once, not in the suite.
- `/auth/login` failures before the callback (G9) and the platform being down at sign-in.
- Production TLS (`__Host-` cookies over https): the suite runs `APP_ENV=test` over plain http.
- The Go orders-demo is not built, so the Go side of "the same SPA on both backends" is untested; the
  application only depends on the committed `openapi.json`, the auth endpoints and the cookie rules.
